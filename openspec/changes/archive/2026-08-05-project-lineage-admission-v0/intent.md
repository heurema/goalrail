## Source Evidence

- **SE-1 — Owner observation:** Goalrail was initialized in a newly created Deltacue repository, but another Codex task using a linked worktree for the same commit reported Goalrail uninitialized and non-working.
- **SE-2 — Owner correction:** Once Goalrail initializes a project, Goalrail is a durable project-governance invariant across clones, worktrees, developers, and tools. Material code work must use one Goalrail intent and change flow; another tool may execute that flow but may not replace it with a parallel intent authority.
- **SE-3 — Owner traceability requirement:** Every material work unit must remain reconstructable as one chain connecting project policy, intent, change, provider sessions/runs, commits, pull request, comments/reviews, checks, terminal receipt, and owner decision. An unlinked material change is a defect; legitimate exceptions must be explicit and deterministic.
- **SE-4 — Owner setup decision:** In a managed clone on a clean machine, a supported agent should detect missing prerequisites, ask permission for an exact setup, install the approved known components itself, verify them, and then return to the original feature request.
- **SE-5 — Repository facts:** CTX-1 through CTX-7, CTX-11, CTX-13, and CTX-14 show that current identity and attachment are local, ordinary work is not admitted through Goalrail, only the OpenSpec overlay reaches a Deltacue clone, existing lineage covers intent through terminal receipt but not the complete project work unit, and installation remains a separate authority.
- **SE-6 — Owner critique evidence:** CTX-10 recommends one deterministic verifier at both local and shared boundaries, treats hooks or `prek` as early feedback only, permits later identifiers through backward references, and keeps every exception visibly non-valid.

## Non-Goals

| ID | Boundary | Evidence |
|---|---|---|
| NG-1 | No claim that Goalrail can physically prevent a user or arbitrary process from writing local bytes in an uncontrolled Git clone. The enforceable guarantee is that supported agents fail closed and unlinked material work cannot pass the protected project admission boundary or be represented as Goalrail-conformant. A controlled write gateway or sandbox is outside this slice. | SE-2, SE-6, CTX-4, CTX-10, CTX-11 |
| NG-2 | Local Git hooks, commit trailers, agent instructions, or `prek` are not the authoritative boundary and are never presented as unbypassable. `prek` may be an optional adapter, not a second mandatory clean-machine dependency. | SE-6, CTX-10, CTX-11 |
| NG-3 | No parallel spec, intent, provider-local plan, or copied Goalrail artifact becomes a second canonical source of project meaning merely to complete lineage. The chain references existing authoritative artifacts and their immutable identities. | SE-2, SE-3, SE-5, CTX-6, CTX-14 |
| NG-4 | No silent install, login, authentication flow, credential issuance or refresh, unlisted dependency, system-wide configuration, or global agent modification is authorized by a feature request or by general setup consent. | SE-4, CTX-12, CTX-13 |
| NG-5 | No broad exemption exists for documentation, formatting, generated files, small diffs, or favored tools. Materiality and any standing exclusions must be deterministic, committed, narrow, and testable; uncertain classification fails closed or requires an explicit recorded exception. | SE-2, SE-3, SE-6, CTX-9, CTX-10 |
| NG-6 | No new central server, database, dashboard, workflow engine, authorization product, or controlled execution environment is introduced until a narrower implementation proves it necessary. | SE-6, CTX-10, CTX-14 |
| NG-7 | The project contract remains provider-neutral. OpenSpec may remain the selected planning compiler and Codex or Claude may have thin bootstrap adapters, but none becomes a permanent canonical Goalrail domain type. | SE-2, SE-5, CTX-14 |
| NG-8 | This planning change does not itself authorize implementation, installation on the owner's machine, mutation of Deltacue, commit, push, pull-request creation, CI activation, branch-protection changes, release, publish, deploy, credential use, or any other external effect. | SE-1, SE-4, CTX-1, CTX-13, CTX-14 |
